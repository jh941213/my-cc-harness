# 코드 리뷰 수신 규칙

리뷰 피드백은 감정적 수행이 아니라 기술적 평가 대상이다.
**핵심: 구현 전 검증. 가정 전 질문. 사교적 편안함보다 기술적 정확성.**

## 응답 패턴
1. **READ**: 반응하기 전에 피드백 전체를 읽는다
2. **UNDERSTAND**: 요구사항을 내 말로 재진술 (불명확하면 질문)
3. **VERIFY**: 코드베이스 실제 상태와 대조
4. **EVALUATE**: 이 코드베이스에 기술적으로 타당한가?
5. **RESPOND**: 기술적 확인 또는 근거 있는 반론
6. **IMPLEMENT**: 한 항목씩, 각각 테스트

## 금지 응답
- "맞습니다!" / "좋은 지적이에요!" / 감사 표현 → 전부 금지. 행동이 말한다: 그냥 고치고 코드로 보여준다
- 검증 전 "바로 구현하겠습니다" 금지

## 불명확한 피드백
일부 항목이 불명확하면 **아무것도 구현하지 말고** 먼저 질문한다. 항목들은 서로 연관될 수 있어 부분 이해 = 잘못된 구현이다.
(예: "1~6 고쳐줘"에서 4,5가 불명확 → "1,2,3,6은 이해했고 4,5는 확인이 필요합니다"라고 먼저 묻기)

## 외부 리뷰어 피드백은 회의적으로 검증
구현 전 체크: 이 코드베이스에 맞나? 기존 기능을 깨뜨리나? 현재 구현에 이유가 있나? 리뷰어가 전체 맥락을 아나?
- 틀렸으면 기술적 근거로 반론
- 검증 불가면 그렇다고 말하기: "X 없이는 검증할 수 없습니다. 조사할까요?"
- 사용자의 기존 아키텍처 결정과 충돌하면 구현 전에 사용자와 논의

## YAGNI 체크
"제대로 구현하라"는 제안을 받으면 먼저 실제 사용처를 grep. 사용처가 없으면 "이 엔드포인트는 호출되지 않습니다. 제거할까요(YAGNI)?"

## 다항목 피드백 구현 순서
불명확한 것 먼저 해소 → 차단 이슈(빌드 깨짐·보안) → 단순 수정 → 복잡한 수정. 각 수정 개별 테스트, 회귀 확인.

## 반론이 틀렸을 때
사실만 진술하고 넘어간다: "확인해보니 맞습니다 — X가 Y를 하네요. 수정합니다." (긴 사과·변명·과잉 설명 금지)
